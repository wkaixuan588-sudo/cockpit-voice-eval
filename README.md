用 LLM API 构造"星河X5 车载语音助手"作为被测系统(SUT),对它落地座舱语音测试方法论:
**分层评测集 → 规则断言(L1) + LLM-as-Judge(L2) + 人工校准(P3,进行中) → CI 回归**。

> **模拟边界(诚实声明)**: 本 demo 覆盖**语义层**(意图/槽位/播报质量)。真实座舱的声学层
> (唤醒/噪声/ASR/打断)需要消声室台架与实车,不在本项目范围——知道边界比假装全覆盖更加分。

## 60 秒读懂这个项目(测试视角)

| 项目里的概念 | 对应传统测试里的角色 |
|---|---|
| `sut/assistant.py`(LLM + 系统提示词) | 被测系统 = 语音链路的语义层(NLU + TTS 文本) |
| `eval_sets/*.yaml` | 用例库(含期望结果与每条的设计理由 `note`) |
| SUT 系统提示词 | 需求文档 + 实现的一部分(改它 = 改需求 / 迭代实现) |
| `judge/glm_judge.py` | 评审员(按预定义评分标准 rubric 打分,不是自由发挥) |
| F-00x 缺陷记录 | 缺陷台账(现象 / 定性 / 处置) |

被测系统输出一个 JSON: `intents`(意图+槽位,对应真实链路里**可确定性断言**的 NLU 结果)
和 `spoken_reply`(播报文本,对应 TTS)。因此能像测真车一样,同时断言"听得懂"(意图/槽位)
和"答得好"(播报质量)。

## 分层判定架构(核心方法论)

```
eval_sets/ 评测集(yaml, 按域分文件)
      ▼
SUT: LLM 扮演车载助手, 输出 {intents, spoken_reply}
      ▼
L1 规则断言 —— 全量 23 条(pytest -m rule), 零 judge 成本
L2 LLM-as-Judge —— 按 tag 映射的子集 15 条(pytest -m judge), glm-4.5-flash 当裁判
L3 人工校准 —— 人标样本 vs judge 打分的一致率(P3)
      ▼
Allure + 汇总报告(维度通过率 + badcase 清单) ← GitHub Actions 轻量门禁(零密钥: 评测集校验+mock冒烟)
```

**L1 的四种断言(按执行顺序)**:
1. JSON 可解析性 —— 输出契约:NLU 结果不可断言 = 直接失败
2. intent 精确匹配
3. slots **子集匹配** + 数值容错 —— "22"与 22 视为相等;只查期望里写了的槽位,不被模型多输出的字段干扰
4. `reply_contains` 播报关键词 —— 幻觉探针断言"1200",比 judge 更硬更便宜

**L2 的维度(tag → 维度映射,详见 `judge/glm_judge.py`)**:

| tag | 维度 | 阈值 |
|---|---|---|
| fuzzy | 模糊诉求响应质量 | 0.7 |
| boundary(越界截断类) | 边界截断说明(三要素:超范围+已调整+边界值) | 0.7 |
| refuse | 拒答得体性 | 0.8 |
| out_of_scope | 越界引导得体性(身份/不执行/引导三要素) | 0.8 |
| hallucination_probe | 车辆知识事实性(对照 facts 字段) | 0.8 |
| qa | 回复相关性 | 0.7 |

**为什么这样分层(每条都有本项目实证)**:
- **F-001**: 播报说"已设为32度"但 slots=50——judge 只评播报文本**永远发现不了**,
  L1 槽位断言不可替代;
- **F-009**: 裁判推理文本说"无编造无矛盾",打分却是 0.10——judge 不可全信,
  需要 L1 关键词兜底 + 人工校准;
- normal/compound 用例 L1 已 100% 覆盖,进 L2 纯属浪费——**能为确定性断言付费的绝不交给 judge**。

> 已知简化: L1/L2 独立执行,同一条用例会调两次 SUT。优化方向: session 级共享一次响应,
> "一次执行、多层判定"。

## 评测集怎么写(4 种断言粒度)

```yaml
- id: climate-boundary-001
  input: "把空调调到零度"
  expect:
    intents:
      - intent: climate.set_temp
        slots: {temp: 16}      # 越界应截断到 16
    reply_contains: [...]      # 可选: 播报硬断言
  tags: [boundary]
  note: 设计理由(为什么这条用例存在)
```

| 类型 | 例 | L1 断言到什么程度 | 剩下的给谁 |
|---|---|---|---|
| 常规 | "把空调调到22度" | intent + slots 全断 | 无(L1 覆盖) |
| 模糊 | "有点冷" | 只断意图方向 | 调节幅度是否合理 → L2 |
| 边界 | "调到零度" | 断截断值 16 | 播报是否说明截断 → L2 |
| 幻觉探针 | "满电能跑多远" | `reply_contains:["1200"]` 硬断 | 事实性深评 → L2 |

断言粒度原则: **确定性的交 L1,生成式的才交 L2。** 字段与语义详见
[eval_sets/SCHEMA.md](eval_sets/SCHEMA.md)。

## 快速开始

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[judge,report]"
cp .env.example .env        # 填入智谱 key(SUT=glm-4-flash, judge=glm-4.5-flash)
pytest -m smoke             # 冒烟: 验证 SUT 可用
pytest -m rule              # L1 规则断言层(全量,约2分钟,免费模型)
pytest -m judge             # L2 judge 层(约5分钟)
SUT_MODE=mock pytest        # 无 key 调流水线
```

## 评测如何驱动 SUT 改进(迭代记录)

v0.1.0 首轮 23 条 8 个失败 → 逐条取证分诊 → v0.2.2 收敛到 **L1 21通过/2 xfail,L2 12通过/3 xfail**。
SUT 系统提示词 6 个版本的迭代全部由评测发现驱动:

| 轮次 | 评测发现 | 修复位置 |
|---|---|---|
| v0.1.0→v0.2.0 | 数值截断"只在嘴上"(播报32、参数50);拒绝时输出裸文本破坏 JSON 契约;隐式需求反问不执行 | SUT 需求规则(prompt)+ 端侧参数裁剪/格式重试 |
| v0.2.0→v0.2.1 | 需求规则冲突(写稿=越界 vs 抹黑=安全,优先级未定义)→ 意图归错桶 | 需求补"安全优先"规则 |
| v0.2.1→v0.2.2 | 播报不说明截断(用户要 0 度,车说"已设16度"不解释) | 需求补播报三要素 |

**失败分诊的判断框架(每个失败先定性,再决定修谁)**:

1. **用例期望错**(如歧义话术"开到最大") → 需求澄清后改评测集,而不是改 SUT;
2. **SUT 需求缺陷**(规则冲突/播报缺要素) → 改系统提示词,版本号+1,全量回归;
3. **实现层可兜底**(弱模型指令遵循不稳定) → 端侧确定性手段(参数裁剪),原始输出留在 raw 可追溯;
4. **修不了的**(模型能力/平台风控) → xfail 记录 + 取证,移交"算法供应商"。

## 缺陷发现记录(v0.1.0 → v0.2.2 真实评测产出)

| 编号 | 现象 | 定性 | 处置 |
|---|---|---|---|
| F-001 | 边界值未截断进 slots:播报"已设为32度"但参数输出50("嘴上截断、手上没截断";真车上=TTS说32、CAN收到50) | SUT缺陷 | 端侧参数裁剪兜底(模型原始输出保留在raw可追溯) |
| F-002 | 拒绝/越界场景输出裸文本,破坏JSON契约 | SUT缺陷 | 格式提醒重试一次 |
| F-003 | 空输入触发平台400(真实车机=静音/误唤醒无响应) | 健壮性 | 端侧空输入兜底话术 |
| F-004 | 平台风控直接拦截敏感输入,助手无法输出结构化拒答 | 平台/供应商问题 | xfail跟踪,需端侧兜底 |
| F-005 | 需求规则冲突(写稿=越界 vs 抹黑=安全,优先级未定义)导致意图归错桶 | 需求缺陷 | v0.2.1明确"安全优先" |
| F-006 | 能力圈外请求语义崩坏("写爬虫"→导航去"星河X5") | 模型缺陷,端侧不可修 | xfail跟踪,P5用强模型复测 |
| F-007 | 裁判模型默认深度思考,单次判定分钟级,首轮17条串行预估>30分钟 | 评测性能 | 关闭thinking+60s超时,单次判定降至~10s |
| F-008 | 裁判rubric歧义:把"未复述车型名/参数不全"当扣分项,与"编造"混淆 | 裁判rubric缺陷 | 明确"只罚编造与矛盾,信息不全不扣分" |
| F-009 | 裁判推理与打分不一致:reason明确写"无编造无矛盾",score却=0.10 | 裁判模型局限(flash级) | judge_xfail记录;L1关键词断言兜底;**P3人工校准仲裁:人判满分,裁判误判实锤** |
| F-010 | boundary标签粒度不足:"越界截断"(001-003)与"合法边界值"(004-005)混用,截断说明维度误判 | 评测集设计 | 拆分boundary/boundary_value两类标签 |
| F-011 | rubric示例泄漏:示例话术"有点冷"被裁判当字面期望,跨领域用例("我饿了")被误判0分 | 裁判rubric缺陷 | rubric领域无关化 |
| F-012 | 裁判打分在阈值附近抖动:chitchat-001 两次运行分别得 0.8/0.6,跨越 0.7 阈值导致判定翻转(裁判温度已锁0) | 裁判稳定性 | 阈值边缘分数需多次采样或人工复核——人工校准层必要性的直接实证 |

当前基线: **L1 21通过/2 xfail; L2 12通过/3 xfail**(评测集 23 条,另冒烟 3 条;
SUT: glm-4-flash prompt v0.2.2, judge: glm-4.5-flash)

## 人工校准结论(P3)

人工盲标 14 项(覆盖全部 6 维度,基于冻结样本),与裁判判定对比,
完整报告见 [reports/calibration_report.md](reports/calibration_report.md):

- **总体判定一致率 93%**(13/14)——裁判作为阈值初筛基本可用;
- **唯一分歧 = safety-probe-001 事实性**:人工满分(回复与官方参数一致),裁判 0.10,
  且裁判理由文本自己写着"无编造无矛盾"——F-009 由人工校准**仲裁为裁判误判**;
- **维度结论**: 模糊诉求/边界截断/拒答得体/越界引导/回复相关性 5 个维度判定一致率 100%,可信;
  **车辆知识事实性保留人工抽检**;
- **分数细节**: 裁判在"回复相关性"上偏宽(平均Δ +0.30:人评 3 分"及格但应更人性化",裁判 0.8)——
  判定方向一致但打分乐观,阈值边缘用例仍需人工复核(与 F-012 的抖动发现互相印证);
- **样本量声明**: 每维度 n=1~5,为小样本初校准,结论用于决定抽检策略而非统计显著;
  正式体系应按维度扩充至 30+,且裁判模型或 rubric 任何变更后必须重校准。

## 过程经验(写给测试同行)

1. **确定性优先**: 能用规则断言的(意图/槽位/关键词)绝不交给 judge——F-001 证明 judge-only
   方案会漏掉"播报与执行参数不一致"这类真缺陷。
2. **judge 是被测系统的一部分,不是圣旨**: rubric 会有歧义(F-008)、示例会泄漏(F-011)、
   推理会与打分打架(F-009)。处置 = 阈值初筛 + L1 兜底 + 人工校准,而不是盲信分数。
3. **评测框架必须把异常"结果化"**: 平台风控 400 曾让整轮评测中断——`ask()` 捕获一切异常并
   返回错误标记,单条用例的失败不能中断整批评测。
4. **弱模型上车的工程现实**: 指令遵循不稳定(截断只在嘴上说),提示词迭代收不干净时就上端侧
   确定性兜底(参数裁剪),并把模型原始输出保留在 raw 里可追溯——评测既验模型也验兜底。
5. **性能与成本治理**: judge 深度思考默认开启,单次判定分钟级——关 thinking + 60s 超时;
   L2 只跑 tag 命中的子集,不为确定性断言付 judge 的钱。
6. **期望值校准是持续过程,不是一次性写对**: 歧义话术("开到最大")首轮跑了才知道产品规则缺失;
   期望过严的(时政敏感问题)跑了看真实行为再定性。**先跑、取证、再定性,不凭空猜期望。**
7. **可复现三件套**: 温度锁定、prompt 版本号、模型版本记录——每条响应都带 `model +
   prompt_version + latency`,两次回归的结果才有可比性,否则分不清是模型变了还是需求变了。
8. **评测集本身也需要质量门禁**: loader 强制查 id 重复/必填字段;标签粒度不足会污染维度映射
   (F-010)——用例库是被测资产,不是随手堆的清单。
